## a) Asenna Ghidra

**Ghidra** on Yhdysvaltain Kansallisen turvallisuusviraston (NSA) alun perin kehittämä takaisinmallinnustyökalu, joka on myöhemmin julkaistu avoimella lähdekoodilla (Newman 2019). Nimensä mukaisesti, tämä tehtävä aloitetaan asentamalla kyseinen ohjelma omalle virtuaalikoneelle: 

```bash
sudo apt install ghidra
```

Tarvittavat Java-kirjastot löytyivät ainakin Kalista jo valmiina, joten näitä ei tarvinnut lähteä erikseen asentelemaan. Ghidran voi siis suoraan vain asennuksen jälkeen käynnistää komennolla ```ghidra```:

## b) rever-C

Tehtävänanto on tutkia jo **h3 No Strings Attached** -tehtävässä ladattua ja purettua **ezbin-challenges**-pakettia. Tarkemmin ottaen paketin sisällä olevaa UPX-purettua **packd**-tiedostoa ja sen lähdekoodia Ghidran avulla.  Ghidra ei ole ennestään tuttu työkalu, mutta uskoisin, että tämä aloitetaan luomalla projekti, jonka itse nimesin vain hyvin mielikuvituksellisesti h4. Tämän jälkeen tarkoitus on tuoda packd-tiedosto valitsemalla Ghidrasta **File** > **Import File...** > menemällä hakemistoon, johon packd on purettu, sieltä valitsemalla **packd** ja lopuksi painamalla **Select File To Import**.

Kun painetaan **Yes**, main-funktio löytyi:

```bash
undefined8 main(void)

{
  int iVar1;
  char local_28 [32];
  
  puts("What\'s the password?");
  __isoc99_scanf(&DAT_0010201d,local_28);
  iVar1 = strcmp(local_28,"piilos-AnAnAs");
  if (iVar1 == 0) {
    puts("Yes! That\'s the password. FLAG{Tero-0e3bed0a89d8851da933c64fefad4ff2}");
  }
  else {
    puts("Sorry, no bonus.");
  }
  return 0;
}
```

Kuten tulosteesta voidaan nähdä, muuttujien nimet ovat Ghidrassa melko epäselviä, eikä näkyvillä oleva kieli vastaa suoraan alkuperäistä C-kieltä. Tässä tehtävässä täytyy tehdä oma valistunut arvio siitä, millaisia muuttujanimet ovat voineet olla ja mitä C-kielen funktiokutsuja ohjelmassa on käytetty.

Aluksi **&DAT_0010201d** vaikutti sellaiselta tiedolta, josta ei voi päätellä juuri mitään. Tutkimalla binääriä kuitenkin tarkemmin huomasin, että Ghidra antaa suoraan merkit ASCII-muodossa ja vielä "selkokielisinäkin":

**%19s** siis kertoo scanf-funktiolle, että syöte luetaan merkkijonona ja että syötteestä hyväksytään enintään 19 merkkiä. Miksi 19, kun tilaa on varattu kuitenkin 32 merkille? Tämä on todennäköisesti ohjelmoijan omaa tajunnanvirtaa, jota edes Ghidralla ei pystytä takaisinmallintamaan. Loput koodista arvioin toimivan seuraavanlaisesti:

```bash
int main(void)

{
  int password;
  char input [32];
  
  printf("What\'s the password?");
  scanf("%19"s,input);
  password = strcmp(input,"piilos-AnAnAs");
  if (password == 0) {
    printf("Yes! That\'s the password. FLAG{Tero-0e3bed0a89d8851da933c64fefad4ff2}");
  }
  else {
    printf("Sorry, no bonus.");
  }
  return 0;
}
```

Ohjelma siis pyytää salasanaa, lukee syötteen scanf-funktiolla ja vertaa sitä merkkijonoon **piilos-AnAnAs** käyttäen strcmp-funktiota. Funktio vertaa kahta merkkijonoa merkki merkiltä ja palauttaa arvon 0, jos merkkijonot ovat täysin samat ja tulostaa lipun. Jos merkkijonot eroavat toisistaan, funktio palauttaa jonkin muun arvon ja ohjelma tulostaa virheilmoituksen.
